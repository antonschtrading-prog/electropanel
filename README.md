# Electropanel Web Preview 0.13

**Бесплатный браузерный редактор черновой структуры щита 230/400 В.** Python, сервер, регистрация и внешний API для открытия не нужны. **Программа не является подтверждённым инженерным проектом или монтажной документацией.**

## Запуск

Откройте https://antonschtrading-prog.github.io/electropanel/ в браузере. Для резервной копии сохраняйте проект в JSON. Выберите пример квартиры или коммерческого помещения, откройте «Компоновка».

## Новые функции версии 0.9

1. **Символические контакты потребителей.** Введена отдельная модель `terminalLinks` / `terminalVersion:1`, связанная с устойчивыми ID потребителя, цепи и отходящего аппарата. Каждая запись содержит вид символического контакта L1/L2/L3/N/PE, условный источник и условный вход потребителя. Это **не физические клеммы конкретных устройств**.
2. **Только явное создание.** В редакторе «Контакты потребителей» можно объявить контакты отдельного потребителя или заполнить отсутствующие декларации для уже объявленных маршрутов. Старые проекты при открытии не получают выдуманные контакты. PE не объявляется, пока пользователь отдельно не заявил PE в маршруте цепи.
3. **Аудит целостности.** Выявляются отсутствующие, лишние, устаревшие контакты, неправильные ссылки, повторные входы, конфликт источника относительно объявленного маршрута. После смены фазы или N-шины старые записи **не переписываются молча**: выводится замечание.
4. **Экспорт.** Символические контакты в отдельной CSV-ведомости и SVG-обзоре с явным предупреждением «НЕ МОНТАЖНАЯ СХЕМА». Тексты SVG экранируются, CSV нейтрализует начало формул таблиц.
5. **Совместимость.** Импорт проектов 0.8 и более ранних, версия контактной модели проверяется. Удаление цепи или потребителя удаляет принадлежащие ему записи.
6. **Тесты.** 147/147 Node.js-тестов (18 новых). Структура HTML, синтаксис JS, целостность архива проверены при упаковке.

## Ранее реализовано

- Отдельные потребители, цепи, отходящие аппараты и общие УЗО с миграцией старых файлов.
- Условная компоновка на DIN-рейках, SVG/CSV/JSON, история изменений и импорт ТЗ с предварительным просмотром.
- Декларации фаз/N/PE и аудит принадлежности N-шины группам УЗО.
- Только арифметическая проверка вручную заданных токов, без нормативного подбора.

## Как проверить новую функцию

1. Откройте пример квартиры → «Компоновка» → «Маршруты L/N/PE».
2. Нажмите «Заполнить отсутствующие маршруты». PE автоматически не заполняется.
3. В «Контакты потребителей» нажмите «Добавить отсутствующие декларации» — появятся только L и N.
4. Если хотите лишь зафиксировать намерение провести PE, отдельно нажмите «Заявить PE» у цепи, затем повторно объявите контакты потребителя. **Никакие измерения PE это не подтверждает.**
5. Сохраните JSON, заново импортируйте его; проверьте сохранённые сведения. Экспортируйте CSV/SVG для сверки.

## Самостоятельный запуск тестов (не требуется для открытия)

```sh
node --check app.js
node --test tests/*.test.js
```

## Что пока не реализовано

**Нельзя использовать для монтажа:** нет сертифицированных паспортов и реальных клемм изготовителей, входных связей питания через УЗО/АВДТ, проверки полюсов и коммутации N, сечений проводников, токов КЗ, условий отключения, непрерывности PE, нагрева щита, селективности и полноценной монтажной однолинейной схемы. Условные связи не считаются нормативно допустимыми автоматически.

**Браузерное UI-тестирование:** в текущей среде Chromium ранее блокировал открытие тестовой страницы, поэтому реальные действия мышью/сенсорным вводом в Chrome/Safari на Mac **не подтверждены**. Node-тесты не заменяют эту проверку.

Для надёжности сохраняйте оригинальные JSON отдельно: файлы новой версии могут не открываться в старых выпусках редактора.

## Версия 0.10: питающие связи (добавление к версии 0.9)

- В разделе «Компоновка» новый блок **«Питание отходящих аппаратов · условный граф»**. Сначала явно задайте маршруты L/N, затем нажмите «Заявить питание» для цепи или «Добавить отсутствующие». Никакого автоматического назначения PE нет.
- Декларация отражает условный путь источника фаз к отходящему аппарату и принадлежность нейтрали N-шине своей группы. **Не описывает физические клеммы изготовителя или реально выполненную коммутацию N**.
- При несовпадении групп УЗО и шин N программа отказывает в новом объявлении питания; при изменении уже объявленной схемы показывает `FEED_STALE` / `FEED_CONFLICT`, не подменяя старые данные.
- Ввод питания на групповые УЗО пока не моделируется: аудит всегда оставляет замечание `GROUP_INPUT_UNMODELED`, даже если выходы групп заявлены.
- CSV и SVG экспорты для проверки по отдельности. JSON проекта теперь содержит `feedLinks` и `feedVersion: 1`. Старые проекты загружаются без автоматического создания этих сведений.
- Тестирование: 173/173 Node.js-теста. Это **не доказательство** нормативного соответствия, электробезопасности или корректности монтажа. Подробности — в `REVIEW_v0.10.md`.

## Новое в 0.13 — первый реальный каталог аппаратов

- В локальном `catalog.js` три подтверждённых артикульных записи: Schneider Electric Acti9 iC60N A9F74116, ABB System pro M S201-C16 2CDS251001R0164, IEK KARAT ВА47-29 MVA20-1-016-C. Каждая содержит серию, паспортную ширину, количество полюсов, номинал, характеристику, Icn и ссылку на источник. Это пилотная база, а не полный каталог производителя.
- На вкладке «Компоновка» выберите аппарат, затем конкретный артикул. Для выбранной модели изменятся марка, серия, надпись и стилизованный фасад. Артикул сохраняется в JSON, привязан к логической линии и ведомости.
- Геометрия DIN рассчитывается по целым модулям. 17.5/18 мм сохраняются как атрибуты изделия, но **не применяются как точная CAD-геометрия**. Точные фасады, сертифицированные CAD/STEP, соединительные принадлежности и монтажные расстояния пока не импортированы.
- Проверка несовместимых фазы, ширины или ручного обозначения отмечает конфликт. **Выбор аппарата не проверяет** токи КЗ, кабель, защиту от поражения, температурный режим или соответствие требованиям ГОСТ/ПУЭ.
- Фасады нарисованы нашим CSS и лишь условно различаются по бренду; это **не фотографии и не точные изображения производителей**.

Планы: расширить паспортную базу, прикрепить разрешённые изображения и CAD-геометрию, организовать фильтр серии/номинала, затем связать каталожные параметры с независимыми инженерными проверками.

## Разработка: каталог и предварительная проверка Iкз/Icn (PR №1, не опубликовано)

- Выбор производителя и серии отфильтровывает только реально внесённые записи каталога; выбранный артикул не заменяется при переключении фильтров.
- Для однофазной линии можно выбрать только аппараты с предусмотренной моделью полюсности; это проверка структуры, а не полного подключения N/PE.
- В «Документы» можно независимо вводить ожидаемый ток короткого замыкания в кА, без обязательного заполнения Ib/In/Iz/I2. Значение хранится в `faultInput.ikKa` вместе с цепью при экспорте JSON.
- Программа сравнивает **только явно введённый Iкз** с хранимым значением **Icn** выбранного конкретного автомата. Результаты: `UNKNOWN`, `INVALID`, `FAIL` и `PRELIMINARY_PASS`. Последний означает только арифметическое сравнение, **не разрешение на монтаж**.
- Icn в IEC 60898-1 не взаимозаменяем с Icu/Ics в IEC 60947-2. Не подтверждены условия применения, действительный расчёт Iкз, питание/напряжение, петля КЗ, каскадирование, селективность, кабели, тепловой режим и отключение питания.
- Неверные значения Iкз в JSON теперь отклоняются вместо молчаливого удаления. Старые проекты без `faultInput` продолжают загружаться.
- Новые проверки не используют ИИ в браузере, а CI настроен на события pull request с ограничением 5 минут. Не создаются периодические фоновые задания.

Проверка перед слиянием: `node --check app.js`, `node --check catalog.js`, `node --check protection.js`, `node --test tests/*.test.js`; затем ручной прогон в браузере. Пока эти проверки не подтверждены, PR остаётся черновым.

### Происхождение значения Iкз

Поле `faultInput.source` хранит краткую ссылку на расчёт или протокол, введённую пользователем. Если источник не указан, аудит выдаёт `CATALOG_IK_SOURCE_MISSING`; это не удаляет введённое значение и не превращает предварительную проверку в инженерное подтверждение. Источник пока лишь декларативный, его подлинность и методика не проверяются. Импорт отвергает некорректные типы и источники длиннее 200 символов.

## Разработка: сохранение расчётных исходных данных при изменениях (PR №1)

- Замена артикула, шаблона или размеров аппарата, изменение фазы или мощности **не удаляют молча** прежние декларации Ib/In/Iz/I2 и Iкз. Вместо этого, если расчётные данные уже есть, строка получает `calculationReview: {required:true,reason:...}` и замечание `CALCULATION_REVIEW_REQUIRED`.
- Отметка об обязательной повторной проверке сохраняется в JSON и показывается в компоновке и документах. Она снимается только при явном повторном сохранении расчётных входных данных. При этом инженерное соответствие по-прежнему **не подтверждено**.
- При импорте неизвестный `catalogSku` не отбрасывается автоматически — выводится замечание `CATALOG_UNKNOWN`, и отсутствующий артикул виден в выпадающем списке.
- Дополнительный тест `tests/calculation-review.test.js` покрывает замену артикула, сохранение исходных токов, уведомление о повторной проверке и явное снятие отметки.
- Важный недостаток: статус `calculationReview` — это журнал потребности в перепроверке, а не электронная подпись, экспертная виза или сертификат.

## Продолжение переноса прежнего Electropanel (рабочая ветка, не опубликовано)

1. **Независимый браузерный предпроверочный слой:** `epEngineeringPreflight` проверяет для каждой линии объявленные токи Ib/In/Iz/I2, предварительное сравнение Iкз/Icn, происхождение входных данных и признак устаревшего расчёта. В проектном аудите, карточке компоновки и готовности документов отдельно обозначены блокирующие несоответствия и неизвестные условия. `engineeringApproved` всегда `false`: нормативное соответствие не устанавливается.
2. **Контроль старого Studio JSON:** `legacy-compat.js` распознаёт старую модель `panel.rails/panel.devices/panel.wires`, проверяет уникальность ID, существование реек, размеры по *заявленному* `catalog[model_sku].modules`, пересечения и ссылки на аппараты. При загрузке показывает диагностическое сообщение, **не подменяя текущий проект и не изобретая цепи, нейтрали или проводники**.
3. Оба модуля — обычный JavaScript без Python API, фоновых обращений к ИИ или серверных вызовов. Интерфейс старого `studio.html` из доступных материалов использовал `/api/v28/*` и поэтому напрямую не совместим с GitHub Pages.
4. Регрессионные сценарии в `tests/engineering-preflight.test.js` и `tests/legacy-compat.test.js` проверяют пограничные и ошибочные состояния.
5. **Полный исходный пакет v4.14 найден в библиотеке файлов** (electropanel_core_v4.14.zip, 172 файла). Все 883 Python-теста успешно прошли в текущей среде. Это не подтверждает перенос всех модулей в JS. План сопоставления — `docs/V414_WEB_MIGRATION_AUDIT.md`.
6. Перед слиянием требуется полный Node-прогон, регрессионные сценарии браузера, проверка старых JSON и независимая инженерная проверка нормативных требований. UI не должен показывать прошедшую арифметику как допуск к сборке.

## Проверенный перенос из восстановленного Electropanel v4.14
- Структурная занятость DIN-реек: из layout_capacity_v414.py перенесён в layout-v414.js алгоритм с автономным браузерным выполнением. На эталонах из v4.14 сравнение Python/JS совпало: квартира 36/9/27 с пересечениями 5 и 7; коммерция 36/11/25 с пересечениями 5, 7 и 9. SHA-256 полного проекта пока не реализован и не подделывается.
- Расчёты перегрузки: overload-v30.js воспроизводит алгоритм overload_guard_v30.py для объявленных Ib, In, базового Iz и поправочных коэффициентов с BigInt-десятичной арифметикой; тесты включают величины 1e308 и 1e-600.
- В разделе «Документы» добавлена свёрнутая JSON-форма для независимой проверки v3.0, исходники сохраняются в line.overloadV30. Старые поля overloadInput остаются без подмены.
- Источники и нормативная применимость не верифицированы: даже при PASS по арифметике evidence_status остаётся UNVERIFIED, ready_for_installation — false.
- Пока не перенесены полностью: кабельный расчёт, токи КЗ, отключение питания, полный граф клемм и проводников, селективность, нагрев и подтверждённые паспортные модели. GitHub Pages остаётся целевой платформой без Python-сервера.
